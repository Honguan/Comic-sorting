# 整體設計與操作流程檢查：2026-10-23

範圍：主視窗（漫畫庫、加入面板、章節整合視窗、Komga 匯出、設定）與主佇列（加入、選取、開始、暫停／停止、重試、檢視）。基準為 `a700cec`。沿用 2026-10-01 重構後的結構、Tkinter 與既有設定／歷史格式，沒有新增依賴。

## 架構現況

| 層 | 模組 | 判斷 |
| --- | --- | --- |
| 介面殼層 | `Comic sorting.py`（漫畫庫、整合、匯出、設定）、`translation_queue.py`（主佇列） | 背景工作經事件佇列回到 Tk 主執行緒，邊界清楚。 |
| 檔案核心 | `comic_core.py` | 掃描、整合、CBZ、清理集中一處，介面只呼叫。 |
| 執行器 | `queue_worker.py`、`queue_phases.py`、`queue_parallel.py`、`bt_run_bridge.py` | 五種流程共用 `run_jobs`，不需再拆。 |
| 統計／歷史 | `queue_stats.py`、`queue_history.py`、`model_pricing.py` | 第四輪修正歷史分頁重算總累計；單價視窗無問題。 |

結論：分層合理，沒有需要大幅搬移的模組。問題集中在操作流程的邊角：同一個動作在不同入口行為不一致。

## 發現與處理

| 等級 | 問題 | 處理 |
| --- | --- | --- |
| 整理 | 選漫畫與右鍵「全選…（清除搜尋）」清除搜尋時，自行 `after_cancel` 再呼叫 `apply_filter()`。曾懷疑搜尋已套用時會傳入 `None` 而當機；驗證後確認 `search_text.set("")` 會同步觸發 trace 先建立計時器，因此不會當機。 | 刪除重複的取消碼，只留 `apply_filter()`（它本身會取消計時器）。行為不變，回歸測試覆蓋兩個入口。 |
| P2 | 主要按鈕「加入佇列」只在選取 1 列時可用。多選章節或多部漫畫時按鈕停用，區間欄也停用，使用者必須改按左側「加入選取」。 | 「加入佇列」改為：單一漫畫用章節序號區間；多選章節或多部漫畫時直接加入選取項目。左側「加入選取」保留。 |
| P2 | 多選章節時，主面板區間欄會停用（區間被忽略），但整合視窗共用同一組區間欄卻仍可編輯，輸入值不會生效。 | 整合視窗的區間欄跟主面板同步停用。 |
| P3 | 同一個重排動作，佇列右鍵選單叫「重新選取」，「操作」選單與 README 叫「重試」。 | 右鍵選單統一為「重試」。 |

## 第三輪：結構重構

| 範圍 | 改動 |
| --- | --- |
| 執行器 | `run_jobs` 原本約 235 行，翻譯、前處理、匯出、清理都寫在同一個 try 裡。拆成 `translate_job`（翻譯／前處理；提早結束時回傳 `None`）與 `complete_job`（匯出、清理、最終狀態）；`run_jobs` 只負責排程、暫停、阻擋、計時與檢查點。行為不變，五種流程共用。 |
| 佇列選單 | 「操作」與右鍵選單原本用寫死的索引（如 `entryconfigure(6, …)`）同步狀態。改為 `menu_entry`／`mirror`／`sync_menu`：每個選單項目登記自己的狀態函式，開啟選單時統一計算。 |
| 隱藏元件 | 刪除只為了把狀態傳給選單而建立的隱藏「排程啟動」「調整範圍與順序…」按鈕，以及「進度」「LLM 用量」從未顯示的內嵌框架（`collapsible_frame` 改為 `popup_panel`）。 |

## 第六輪：效能與剩餘版面

| --- | --- | --- |

## 第七輪：大型漫畫庫與高 DPI

以 200 部 × 30 章（6000 章）假漫畫庫量測。掃描本身以磁碟列舉為主（暖快取約 1.3–2.5 秒，`scandir` 佔最多），Python 端無明顯浪費，不改。

| 等級 | 問題 | 處理 |
| --- | --- | --- |
| P2 | 搜尋會展開所有符合的系列；清除搜尋時，這些展開被當成使用者的展開而保留，整個漫畫庫維持全展開，並一次載入全部 6000 個章節列。 | 只在未過濾的樹上記錄展開狀態（`expanded_series`），清除搜尋後回到搜尋前的展開。清除搜尋 0.91 秒→0.13 秒；有選取時 1.04 秒→0.21 秒。 |
| 效能 | 每次重建樹時，每部系列的大小、時間、頁數各自把章節字串重建 `Path`（約 3 萬次）。 | 每部系列只建一次。 |
| 介面 | 175% 縮放下文字由 Windows 點陣放大而模糊。 | EXE manifest 加入 `gdiScaling`（`assets/app.manifest`）：程式仍不宣告 DPI 感知，像素版面不變，但 GDI 文字以實際解析度重繪。相同標籤截圖的邊緣銳利度提高約 7–10%、模糊中間色減少約 9%。 |
| 介面 | 主佇列「流程」選單被拉滿整列，文字浮在中間、箭頭在最右，看不出是選單。 | 改為自然寬度，緊接在「流程」標籤後。 |

不做完整 DPI 感知：除了視窗大小、最小尺寸、欄寬、換行寬度、分隔位置約 70 處，還有約 150 處 `padx`／`pady`、27 處 `padding` 與已儲存的視窗大小都要換算；只換一部分會讓 175% 下的間距只剩原本的 57%。改動面與風險遠大於比 `gdiScaling` 多出的清晰度。
